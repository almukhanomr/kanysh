# Большие corner-point модели: реализация 0–6

## 0. Воспроизводимые измерения

`scripts/generate_scaling_model.py` создаёт реальные DATA/COORD/ZCORN, а не виртуальную
сетку. Профили: 10, 50, 100 и 200 млн ячеек, десять слоёв, пять EQLNUM/FIPNUM,
сдвиг полосы пилларов на 3 м, нулевой пиллар, десять допустимых pinched-ячеек,
три намеренно скрученные активные ячейки. OWC пересекает 10% обычных ячеек.
`analytic.json` содержит GRV, объём выше контакта и STOIIP по регионам, включая
точные рациональные значения. Для сложного столбца используются рациональные
определители и аналитические доли симплекса; производственные функции не вызываются.

Бенчмарк явно задаёт `geometry_policy=exclude_flagged` и `parameters_confirmed=true`.
Три исключения проверяются отдельно, итог регионального расчёта остаётся
`PASS_WITH_EXCLUSIONS`. При strict эти ячейки вызывают ошибку. Calculation pipeline
использует явно выбранные чистые зоны 2–5. Это разные объявленные области расчёта.

```powershell
.venv\Scripts\python.exe scripts/benchmark_scaling.py --sizes 10000000 50000000 100000000 --workers 8
.venv\Scripts\python.exe scripts/benchmark_scaling.py --sizes 200000000 --workers 4
.venv\Scripts\python.exe scripts/benchmark_scaling.py --sizes 100000 --workers 1 --profile
```

Каждый размер запускается отдельным процессом. В JSON сохраняются время, sampled
peak RSS дерева процессов (интервал 100 мс), статус каждой стадии, аналитические
ожидания, аппаратная платформа и хеш исходников. Отчёт обновляется после каждой
стадии; непройденные стадии остаются `NOT RUN`, общий неполный прогон — `INCOMPLETE`.
Пять сценариев имеют общие OWC/свойства и отдельные результаты: этот профиль измеряет
переиспользование геометрии. Пять разных уровней контакта — отдельный, пока не выполненный
performance-профиль; корректность разных контактов проверяют тесты.
Профиль содержит top cumulative функций в JSON; полные `.prof` находятся в
`.data/scaling-profiles/`. Для сцены явно выбран диапазон ячеек `[100,1000)`;
расчёты используют всю выбранную область, без прореживания.

Для исходного кода можно задать `PYTHONPATH` на `src` исходного checkout и запустить
тот же скрипт. `--stages generate import model_qc` позволяет отдельно измерять
стадии, оставляя остальные `NOT RUN`. Замеры и ограничения перечислены в
[BENCHMARKS.md](BENCHMARKS.md).

## 1. Независимая проверка без Qhull

`calculations/cornerpoint_reference.py` вычисляет определитель в float64 и точную
барицентрическую долю тетраэдра в полупространстве. Случай двух вершин выражен
полиномом без деления на разность их глубин: одинаковые глубины и вершины на
контакте не требуют возмущений. Масштабирование глубин предотвращает переполнение.
Рабочий CPU/GPU алгоритм строит отсечённые тетраэдры; независимый алгоритм не
вызывает рабочие функции объёма. Общая только объявленная декомпозиция ячейки.

Прежний ConvexHull сохранён в `tests/scientific/hull_reference.py`. Сравнение на
случайных геометриях использует rtol=1e-10. Для метровых ячеек в UTM старый алгоритм
округляет мировые координаты точек пересечения ещё до Qhull; отдельный тест
переносит геометрию в локальные XY **до** построения эталонных пересечений и
использует тот же допуск. RTOL/ATOL научной валидации не изменены.

## 2. Процессы и детерминизм

`execution.max_workers`: `null` выбирает число процессов по ядрам, числу блоков и
доступной RAM; положительное число задаёт верхний предел. На Windows учитывается предел реализации пула — 61 процесс. `spawn` работает на
Windows и Linux. Дочерние процессы открывают неизменяемый Zarr самостоятельно,
сохраняя открытые дескрипторы до завершения пула. Между координатором и каждым процессом используется отдельный Pipe: общий семафор Queue не нужен. Не больше двух блоков
на процесс находятся в работе/ожидают редукции; обрыв канала или выход процесса завершают операцию с WORKER_CRASH. Число потоков BLAS/OMP и Blosc в дочерних процессах равно единице, чтобы пул процессов не создавал дополнительные пулы декодирования.

Regional/reconcile, QC, diff, wells, volumetrics и независимая валидация используют
общий mapper. Границы блоков определяются хранилищем; результаты редуцируются по
возрастающему смещению независимо от порядка завершения процессов. Числовые суммы
используют `math.fsum`/малые floating-point expansions. CSV записывает координатор. CPU-проверки в calculation_run наследуют max_workers плана; их устройство остаётся CPU.
Метки кластеров остаются исходным `ndimage.label`, поэтому их нумерация сохраняется.

Tornado/MC читают модель одним проходом для всех вариантов. Ограниченный LRU хранит
до 32 интегралов блока, отдельно для рабочего и независимого алгоритмов. Для разных
контактов кэш остаётся ограниченным. Ошибки реализаций сохраняются индивидуально,
draws не пересэмплируются. Память региональных редукций не растёт с числом блоков.

Прогресс/ETA пишет координатор через `execution/progress.py`. Краткий Windows
sharing violation при чтении старого progress.json обрабатывается ограниченным retry.

## 3. Потоковый EGRID и ASCII

Большие EGRID импортируются операцией `eclipse_import`, без XTGeo. `format=auto`
распознаёт расширение `.EGRID`; также можно явно задать `format=egrid` или `ascii`.
ROFF и старый native-manifest путь `grid_import` сохраняют прежний лимит XTGeo.

Пример дополнительных полей к обычному запросу `eclipse_import`:

```json
{
  "format": "egrid",
  "path": "MODEL.EGRID",
  "property_files": [
    {"path": "MODEL.INIT", "file_revision": "<revision from source_scan>", "format": "init"},
    {"path": "SWAT.INC", "file_revision": "<revision from source_scan>", "format": "grdecl", "keyword": "SWAT"}
  ]
}
```

Остальные обязательные поля: source/project IDs, file_revision EGRID, CRS, datum,
length_unit, z_direction и assumptions. Повторное объявление свойства отклоняется.
ACTNUM должен присутствовать или иметь явное подтверждённое пользователем значение
в `defaults`; отсутствие ACTNUM не превращается автоматически в «все активны».

Reader проверяет Fortran markers, типы INTE/LOGI/REAL/DOUB/CHAR/MESS, оба порядка
байтов, размеры записей и массивов. COORD/ZCORN/ACTNUM и свойства сохраняются в
дисковых mmap; максимальная отдельная бинарная запись — 16 MiB. INIT поддерживает
полную и ACTNUM-сжатую раскладку. В неактивных ячейках без исходного INIT значения
свойства остаются NaN, регион 0 обозначает отсутствие региона. Значения активных
ячеек не подставляются. LGR, dual-porosity, несколько reservoirs, COORDSYS и
цилиндрические координаты отклоняются явно. NNC не применяется к статическим
объёмам и отражается среди неприменённых keywords.

Ревизии и SHA256 фиксируются для всех прочитанных файлов и повторно проверяются
перед публикацией. Сохранность проверяется для основных и дополнительных свойств,
регионов и Kz/Kx. `region_ids`, `z_convention`, `missing_properties` входят в summary.
REAL геометрия EGRID сохраняет исходную точность float32, после декодирования
вычисляется в float64; недостающая исходная точность не выдумывается.

Для ASCII числовые строки COORD/ZCORN объединяются в bounded текстовые батчи и разбираются NumPy, D-экспоненты поддержаны;
RLE и BOX/EDIT сохраняют строгие счётчики и исходную семантику. Чтение строк
ограничено 1 MiB. После разбора и явных defaults scratch maps открываются read-only:
освобождение прочитанных страниц не вызывает flush больших файлов на Windows. При записи mmap flush ограничен изменённым выровненным диапазоном; бинарные записи объединяются до bounded write-блоков.

## 4. Кластеризация ACTNUM

Выбран допустимый в ТЗ вариант с явным предполётом RAM перед выделением полной
ACTNUM/labels. Консервативная оценка — 80 байт на ячейку, плюс базовая память и
рабочие процессы. Если бюджет превышен, возвращается `INSUFFICIENT_MEMORY` с полем,
оценкой и remediation. При достаточной памяти результат вычисляет тот же
`scipy.ndimage.label` с шестью соседями; приближённой кластеризации нет.

## 5. CUDA

`regional_volumes` и `volumetrics_calculate` на импортированных corner-point сетках
поддерживают `execution.device_policy=require_gpu`. Это доступно и через план на
импортированных свойствах. CUDA использует один координатор на устройство:
`max_workers` должен быть `null` или `1`. CPU-процессы применяются в CPU-пути.

`execution/cornerpoint_gpu.py` обрабатывает float64 тетраэдры батчами с учётом
свободной VRAM. Каждый вычисленный блок/контакт сверяется с CPU float64 при
неизменённых RTOL/ATOL. Расхождение — `VALIDATION_FAILED`, нехватка VRAM —
`INSUFFICIENT_MEMORY`; численного молчаливого fallback нет. Regional дополнительно
выполняет независимую барицентрическую проверку. CPU сверка остаётся обязательной,
поэтому наличие CUDA не означает обещанного ускорения всего расчёта.

DEVICE_MATRIX и NO_COMPATIBLE_GPU отражают поддерживаемые операции. QC, diff,
wells и Cartesian imported volumetrics остаются CPU. GPU-тесты помечены `gpu` и
пропускаются без CUDA; тест расхождения проверяет отказ публикации.

## 6. Ресурсы и диагностика

`diagnostics.resources` и `compute_targets_list.resources` возвращают ядра,
доступную/общую RAM, диск home, рекомендованные max_workers/block_cells. VRAM
запрашивается при уже загруженном CUDA runtime; ранняя диагностика не импортирует
torch ради этой информации.

`compute_targets_list` дополнительно принимает project_id, properties,
operation и execution и возвращает model_estimate. Время основано на предыдущем
измеренном прогоне той же операции на той же модели и явно помечено приблизительным;
сохраняются устройство, workers и число сценариев исходного измерения. Без
измерений время равно null, статус `NOT RUN`, константа скорости не подставляется.

Бюджет рабочей памяти — 50% **доступной** RAM, не всей установленной памяти.
Проверки учитывают процессы, рабочие блоки, кластеры QC и результаты ансамбля.
Перед разбором геометрии оценивается место для scratch/Zarr/публикации.
Ошибки `INSUFFICIENT_MEMORY` и `INSUFFICIENT_DISK` содержат field, remediation и bytes.
